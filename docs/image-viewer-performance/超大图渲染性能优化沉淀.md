# 超大图渲染性能优化沉淀

> 主题：SnowShot 图片查看器（imageViewerCore）针对 2.72 亿像素超大图（18334×14865，30~40MB）的加载与渲染性能优化
> 时间：2026-08
> 涉及文件：[imageViewerCore.tsx](../../src/pages/imageViewer/imageViewerCore.tsx)

---

## 一、问题背景

以 `机上Wi-Fi交互方案260618.png`（18334×14865，约 272MP，30~40MB）为基准测试图，用户连续反馈以下问题：

| # | 问题 | 严重度 |
|---|------|--------|
| 1 | 加载时间过长（最初 5%~20% 进度缓慢，后达 6~7s，最严重 20s+ 卡死感） | 高 |
| 2 | 11%、43% 等低缩放下缩放/拖拽卡顿、抖动 | 高 |
| 3 | 61% 缩放时图像模糊 | 中 |
| 4 | 缩放不跟随鼠标中心 | 高 |
| 5 | GPU 进程内存占用 2.1GB+（总 ~4.7GB） | 中 |
| 6 | 旋转、水平/垂直翻转被优化过程破坏 | 中 |

根因归纳：**Canvas 2D 的 `drawImage` 性能与源纹理大小直接相关**，从 2.72 亿像素原图实时采样是卡顿的根源；同时存在 DPR 单位混用、GPU 纹理过度并行分配、链式降采样质量损失等多个叠加问题。

---

## 二、核心技术与解决方案

### 1. 多级缩略图金字塔（Mipmap 策略）—— 卡顿根治

```
首屏快速生成：[1024, 2048]
后台渐进生成：[4096, 8192]（上限，平衡内存与性能）
```

- **选级规则**：渲染时按当前显示宽度 `dstW = imgW × zoom`，遍历缩略图列表，选择**第一个 `level.width ≥ dstW`** 的级别作为 `drawImage` 源；无匹配则回退原图
- **收益**：每帧 GPU 采样量从 2.72 亿像素降到百万级（2~3 个数量级），缩放/拖拽卡顿彻底消除
- **关键细节**：
  - 每级保持原始宽高比，`scale = maxDim / fullMaxDim`
  - **所有级别从原图直出**，禁止链式放大（4096→8192→12288 的累积采样会导致 61% 缩放模糊）
  - 曾尝试 12288 级（单级 GPU 纹理 488MB），权衡后移除

### 2. 两阶段渐进式加载 —— 首屏 1s 可交互

- **阶段一（同步）**：`buildInitialLevels` 仅生成 [1024, 2048]（~1s），完成后立即 `setLoading(false)`
- **阶段二（后台）**：`setTimeout` 延迟 200ms 后 `buildDeferredLevels` 生成 [4096, 8192]，完成后：
  - 释放首屏低级别 canvas（`level.canvas.width = 0` 回收 GPU 纹理）
  - 排序合并缩略图列表，`requestAnimationFrame(scheduleRender)` 刷新
- **踩坑**：5 个 `createImageBitmap` 并行分配 ~1GB GPU 纹理导致 20s+ 卡死。**禁止并行 `createImageBitmap` 多级缩放**，改用 canvas 同步生成 + 两阶段调度

### 3. 渲染管线优化

| 技术 | 作用 |
|------|------|
| rAF 节流 | 滚轮事件每帧最多触发一次 React 状态更新，消除抖动；`viewTransformRef` 立即更新保证计算基于最新值 |
| viewTransform 状态合并 | zoom/panX/panY 合并为单一对象，减少重渲染次数 |
| imageSmoothingQuality 切换 | 缩放交互中 `"low"`，停止 200ms 后恢复 `"high"`，降低 GPU 开销 |
| canvas 尺寸缓存 | 缓存设备像素尺寸，避免每帧 `getBoundingClientRect()` 强制重排 |
| 可见区域裁剪 | 仅绘制视口内像素区域（`screenLeft/Right/Top/Bottom` 计算） |
| decoding="async" + decode() | 图像解码移至后台线程，不阻塞主线程；失败回退 `onload` |

### 4. DPR 单位统一 —— 修复鼠标中心缩放

- 坐标体系：`panX/panY/zoom` 为 **CSS 像素**，`cw/ch`（canvas 宽高）为 **设备像素**
- 修复：所有 CSS 像素 × `devicePixelRatio` 统一换算：
  ```
  panX_dp = panX * dpr;  dstW = dstW_css * dpr;
  dstX0 = cw / 2 + panX_dp - dstW / 2;
  sx = ((screenLeft - dstX0) / (zoom * dpr)) * srcScale;
  ```
- 鼠标中心缩放公式（数学上正确，此前失准主因是 DPR 混用）：
  ```
  panX_new = panX * ratio - mx * (ratio - 1)
  ```

### 5. 变换路径（旋转/翻转）与坐标系分离

- 旋转/翻转走独立绘制路径：`ctx.save → translate(中心+pan) → rotate → scale → drawImage(完整源图, 居中) → restore`
- 与平移/缩放坐标系统严格分离（对齐项目"坐标系统分离原则"），避免在 JS 中手动补偿 pan 偏移
- 变换路径绘制**完整源图**（而非裁剪区域），源矩形坐标与目标矩形按同源比例推导（`srcH = srcW × (imgH/imgW)`）

### 6. GPU 内存管理

- 移除 12288 级别：节省 ~488MB
- 后台生成完成后释放 1024/2048 canvas：节省 ~20MB
- 预期峰值从 2.1GB+ 降至 ~1.6GB（原图纹理 1.1GB 为不可避免的硬成本）

## 三、与 Rust 重构版对比（为什么当前方案快）

历史背景：项目曾用 Rust + TypeScript 重构图片查看器（自研 Rust 解码 + IPC 传图），实测 **20MB 图片加载需 1 分钟、内存占用高**，最终回退至浏览器原生解码 + Canvas 渲染方案。

| 维度 | Rust 重构版（已弃） | 当前方案 |
|------|--------------------|---------|
| 解码 | 自研 Rust 解码器 | Chromium 内置解码器（libjpeg-turbo 等，数十年 SIMD 优化） |
| 数据传输 | 解码位图经 **IPC invoke 跨进程传输**（30-40MB 序列化+拷贝，硬瓶颈） | `convertFileSrc` 让 WebView2 直接读本地文件，零拷贝 |
| 渲染 | 链路长、无 GPU 加速路径 | `canvas.drawImage` 走 GPU 加速，仅画视口区域 |
| 采样量 | 每帧全量处理 | 缩略图金字塔降低 2~3 个数量级 |
| 内存 | 解码缓冲 + IPC 拷贝 + 前端持有，多处冗余 | 后台级别完成后主动释放低级别 canvas |

**结论**：Rust 重构版的初衷是"极低内存占用"（规避 WebView2 GPU 进程 ~600MB 开销），但在大图渲染链路中，自研解码 + IPC 传图制造了比浏览器原生能力更严重的瓶颈。正确做法是**各层用最合适的引擎**：解码交给浏览器、采样交给缩略图金字塔、绘制交给 GPU，同时以渐进式加载 + canvas 释放控制内存代价。

## 四、踩坑记录（可复用的经验）

1. **禁止并行 `createImageBitmap` 生成多级缩略图** —— 多张大尺寸 GPU 纹理并行分配会直接导致浏览器卡死（20s+）
2. **禁止链式上采样生成缩略图** —— 后一级用上一级 canvas 放大会累积模糊，必须从原图直出
3. **DPR 单位混用是隐性 bug 源** —— CSS 像素与设备像素混算会让缩放中心漂移、变换错位，必须统一
4. **`transferToImageBitmap` 不在 TS 的 `HTMLCanvasElement` 类型中** —— 使用前确认类型定义，避免编译错误
5. **Promise 必须 await 后赋值 ref** —— 异步函数返回值直接赋 ref 会写入 Promise 对象
6. **GPU 纹理释放** —— `canvas.width = 0` 是释放 GPU 纹理的标准做法
7. **解码失败回退** —— `decode()` 失败时回退 `img.onload` 路径，保证兼容性
